# M7: Lead conversion

- **Goal:** A call rep works in their own screen. They confirm orders by call, add upsell, and see GH₵8 per delivered order they confirmed plus 10% of the upsell value. Auto-confirm, the queue timer and the refusal rule run.
- **Done when** (from PRD section 10, made testable):
  - A rep who confirms an order by call and sees it delivered gets one `base` entry of GH₵8 and one `upsell` entry of 10% of the extra value, both `earned` on delivery. They see both on the Earnings page. An order that the customer confirmed by a YES reply creates no entry (P6).
  - On the fixture the rep earnings are: Adwoa owed 2,024 + 610 - 600 paid = GH₵2,034; Nana 104 + 30 = GH₵134; payable 2,168.
  - Time to first call is the time to the first rep call attempt, counted only inside the operating hours the owner enters. An auto-confirm YES closes the clock as "auto-confirmed" (R10). Target 15 min, alert at 30 (D6).
  - The auto-confirm message goes out at once, also outside operating hours (P4). A NO reply does not cancel. The order goes to the call queue with a "said NO" flag; a rep calls once before any cancel (P2).
  - Refusals: 2 refused deliveries make the customer High risk; 3 turn COD off and send the next order to a manual call; the owner can override and the count restarts at zero (G6, P3).
  - A rep can create an order and add and edit customers (G9). A rep sees only their own orders.
- **Depends on (milestones):** M0, M1 (order state machine, `confirmedAt`, `firstContactAt`, decline and failure reason fields, rep success-rate fix), M2 (services), M3 (rep routing behind the flag `features.repApp`, turned on in M7-T13), M5 (commission posting, payout form, `CommissionEntry` model), M6 (targets, rewards, Operations needs Settings shell)
- **PR:** one PR for this milestone. Branch `feature/m7-lead-conversion` from `develop`, PR into `develop`. Never push to `main`. Do not push before the owner approves.
- **Owner of every task:** builder, with Opus review. No owner column.
- **Source:** `docs/prd/PRD.md` sections 5, 6, 7, 10, 11; `docs/prd/decisions.md`; the area files named in the F-IDs; design doc section 10.
- **Size key:** XS = 2 h, S = 3 to 4 h, M = 5 to 6 h, L = 7 to 8 h. Anything larger is split.
- **Working rules:** `codadmin/CLAUDE.md` applies. Run `npx prisma generate` before `tsc` (a stale client hides type errors). After each migration, apply it by hand to the test database `ecommerce_cod_test` (`cd backend && DATABASE_URL=$(grep -E '^DATABASE_URL=' .env.test | sed 's/^DATABASE_URL=//;s/"//g') npx prisma migrate deploy`); the test setup has no global migrate. Run jest with `--runInBand --forceExit`. Feature branches only; PR into `develop`.

**Auto-confirm split.** Area files put the auto-confirm core in M7 (F-466, F-764, F-452 core) because the rep queue needs it. The M9 brief note lists auto-confirm P2/P4 and WhatsApp replies P5 under M9. This plan builds the core here (send, token page, YES and NO handling, queue flag) and M9 adds the Messages side (templates UI, Conversations, reps replying P5). See the M9 file.
