# M4 task plan: Stock and fulfilment

**Goal**: Know where every unit is. Add stock locations, a stock ledger with levels per location, shipment receiving with a counted quantity, landed cost on that count, stock counts against the 3PL, transfers that the receiver confirms, and the Products, Inventory and Deliveries pages. Stock leaves exactly once per order, at delivery.

**Done when** (PRD §10, made testable):
1. The 9 October shipment (300 shipped at GH₵27.00, shipping 450, other 150) receives with 288 counted and 12 short. The shipment shows `quantityCounted = 288`, `shortQuantity = 12`, landed cost per unit GH₵30.21 (8,700 ÷ 288), an open supplier claim of GH₵324, one ledger entry for GH₵8,700 (DR 1200, CR 1010). Integration test and screenshot.
2. Stock gap per location shows. On the fixture, Logiswift copybook set: our records 100, 3PL count 88, difference 12. The Inventory card says "12 units off". A `stock_gap` Finding for GH₵362.50 (12 × 30.21) exists.
3. The M0 characterization test B is switched on and passes: a 3-set public order that is dispatched and delivered lowers the holder by exactly 3. Deliver, return, re-deliver ends at -3. A repeated `delivered` call adds nothing.
4. The stock migration dry-run prints before and after sums per product and they are equal. The run fails if any differ. After the migration the Logiswift copybook level still reads 100.
5. Fixture sample values hold on the Inventory page: Logiswift on hand 342 and reserved 59; Kofi on hand 99; Kofi copybook 36 on hand, 11 reserved, 20 in transit.
6. A transfer to an agent stays `in_transit` until the receiver confirms. Received below sent makes it `disputed` and needs a reason. Resolve works with "Return to source" and "Write off".
7. No code outside `stockService` writes `StockLevel.quantity` or `Product.stockQuantity` (grep test). `PATCH /api/products/:id/stock` and `PATCH /api/products/shipments/:id/arrive` return 404.
8. Deliveries page: the partner table totals 926 assigned / 376 delivered / 402 failed or returned / 148 out and 48% success on the fixture; Delivered + Failed or returned + Out now equals Assigned for each row.
9. No coverage grid (decision O4). The partners API has no coverage or resolve route, and `DeliveryPartnerProfile` has no fallback flag (grep test). Order region values are normalised to the regions of the store's country; unmapped values go to a review list. "Assign by region" is a Workflow built in M9.

**Depends on**: M0 (Decimal, tenant scope, F-657 test), M1 (state machine, `Finding`, `FeeRule`, `FxRate`, KPI partner rates, `failureReason`), M2 (system user, audit, registry for `products_inventory`), M3 (shell, components, `ConfirmDialog`, command palette, order drawer). M3b (checkout and payments) is not a dependency: M4-T07 reads upsell lines from `OrderItem` rows and M4-T37 places a public order on whichever public form is merged, so M4 can start before M3b merges.

**PR**: one PR for the whole milestone. Branch `feature/m4-stock-fulfilment` from `develop` (after M3 is merged), into `develop`. Never push to `main`. No push before owner approval. Do not merge the order-side stock change without the stock migration (F-305 edge case).

**Owner of every task**: builder, with Opus review.

Legend: XS = 2 h, S = 3-4 h, M = 5-6 h, L = 7-8 h. Run `npx prisma generate` first. Hand-migrate the test database after each new migration. Jest with `--forceExit`.

Scope notes (not in M4): fee rule screen and `cash held` / `oldest unpaid` columns (M5, F-703 and F-704); CSV upload (M5; no partner key, O7); the agent app and agent receipt screen (M10, the receipt API is in M4); suggestion cards (M11); Staff person modal (M6, so "Add partner" uses the existing user service); stock count by agents in the app (not in this release).
