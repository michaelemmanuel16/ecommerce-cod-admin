How I run it (same as M4 and M5)

  1. I orchestrate. Builder agents (Sonnet) write the code. I review every diff.
  2. Up to 3 builders work at once. Each has its own worktree (m6-a, m6-b, m6-c) and its own test database (ecommerce_cod_test_a/b/c).
  3. Only lane A changes the database schema.
  4. Each issue goes through the full sprint: issue review, build, /simplify, then all checks. The checks are build, lint, unit and integration tests, workflow validation, and a browser check with screenshots.
  5. I approve each issue myself when every check passes ("mode A"). Then I merge it into feature/m6-roles-targets-rewards, re-run the checks, update the docs and CHANGELOG, comment on Linear, set the issue to Done, and push the branch as a backup.
  6. After the last issue, I run /cso (security audit) and /qa (fixes bugs) on the local app. Critical and high findings get fixed. Medium and low findings become Backlog tickets.
  7. I open the PR into develop and wait for CI to pass. Then I stop, and the PR waits for your review. Nothing merges, and nothing touches production.
  8. caffeinate keeps the Mac awake for the whole run. progress.md is updated at each step.

Done when (from the M6 plan)

  • The Targets page shows on track or off track for every role and person, against the month target, with margin beside revenue at each level.
  • On the test fixture, the North Star setup gives: annual GH₵1.8M; quarters 360k, 420k, 480k, 540k ("grow each quarter"); October GH₵180,000 ÷ GH₵249 = 723 delivered; 1,721 orders; 56 orders a day.
  • Month close is a job with a dry-run preview. The cash tiers are: rep 100% GH₵300, 120% GH₵500 plus a paid day off; delivery 100% GH₵250, 120% GH₵400 plus a paid day off. Running it twice creates the entries only once.
  • The seven current roles map to position roles, and every user keeps every permission they had. Effective permission is the union of the roles a person holds.
  • An invited person sets their own password. A deactivated user cannot sign in. The last Owner cannot be deactivated.
  • The round-robin position survives a server restart.

Risks and how I handle them

  • The role migration could lock people out or widen access. A script test compares each user's permissions before and after the migration, for all seven roles.
  • Tenant data could leak through the new tables. Each new model has a required tenantId and is in the tenant-scoped list. Two-tenant tests cover it in T24.
  • Month close could pay on wrong numbers. It uses only the M1 KPI services, stops on any error, shows a preview first, and can run twice safely. It is tested with a delivery at 23:30 on the last day of the month.
  • Known tooling problems. The CI test step can hang (COD-190). The pre-push hook fails, so I push with --no-verify only after the full test suite passes. Jest runs with --runInBand --forceExit and a timeout.
