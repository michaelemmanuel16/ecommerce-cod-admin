# M9: Inbox and messages

- **Goal:** Customer messages are tracked from sent to replied. Staff have one inbox for alerts, replies, mentions, reminders and team notes. Workflows run on a real queue. Connections live on one page.
- **Done when** (from PRD section 10, made testable):
  - A customer WhatsApp reply shows in Messages, Conversations, links to the right customer and the message it answers, marks that message `replied`, and notifies the assigned rep or the owner. Test with two tenants and two reps.
  - A team note with an @mention on an order shows in the mentioned person's Inbox, once, and not in anyone else's. A rep sees only their own items; the owner sees all. The bell and the sidebar pill update without reload; if the socket drops they poll every 60 seconds.
  - Every message shows sent, delivered, read, failed or replied, and one definition feeds the tiles, the log and the campaigns (the totals agree).
  - A workflow with a Wait step no longer blocks a worker: the wait is a delayed job and survives a server restart. `http_request` makes a real call with a timeout.
  - "Assign by region" is a Workflow: condition "Region is X" plus action "Assign to" one or more agents or partners, split Evenly or Weighted. Without a matching Workflow the order stays unassigned for the fulfilment lead (D3, O4).
  - The Connections page lists every connection as a card. The old `MessageTemplates` text is in Messages, Templates and the old component is deleted (R8).
  - Auto-confirm on the Messages side: a customer YES or NO is handled as in M7 (P2, P4, P6); a rep can reply to any customer on WhatsApp from Conversations (P5).
- **Depends on (milestones):** M0, M1, M2 (workflow actions go through services), M3 (shell, bell), M4 (partners data), M3b (provider interface, neutral webhook, Paystack adapter), M5 (partner CSV tool), M6 (assignment cursor, roles), M7 (inbound WhatsApp core, auto-confirm core, basic rep inbox), M8 (Meta card)
- **PR:** one PR for this milestone. Branch `feature/m9-inbox-and-messages` from `develop`, PR into `develop`. Never push to `main`. Do not push before the owner approves.
- **Owner of every task:** builder, with Opus review. No owner column.
- **Source:** `docs/prd/PRD.md` sections 5, 6, 7, 10, 11; `docs/prd/decisions.md`; the area files named in the F-IDs; design doc section 10.
- **Size key:** XS = 2 h, S = 3 to 4 h, M = 5 to 6 h, L = 7 to 8 h. Anything larger is split.
- **Working rules:** `codadmin/CLAUDE.md` applies. Run `npx prisma generate` before `tsc` (a stale client hides type errors). After each migration, apply it by hand to the test database `ecommerce_cod_test` (`cd backend && DATABASE_URL=$(grep -E '^DATABASE_URL=' .env.test | sed 's/^DATABASE_URL=//;s/"//g') npx prisma migrate deploy`); the test setup has no global migrate. Run jest with `--runInBand --forceExit`. Feature branches only; PR into `develop`.
