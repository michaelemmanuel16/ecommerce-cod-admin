# M1 decisions made during the unattended run

The owner asked Claude to run through M1 without stopping (2026-10-20). Where a ticket needed a choice, Claude picked the safe default below. Each one can be changed later. Review them before the M1 PR.

## COD-10 — Order state machine

| # | Question | Decision | Why |
|---|---|---|---|
| D1 | What actor is the MCP tool, and can it force a move? | **Revised after a data check.** The MCP tool (and so the daily Logiswift sync) is an `integration` actor. It may make ANY move except into `digital_delivered`, with no reason. Each move outside the F-301 table is flagged `metadata.jump = true` in the history. It cannot use `force`. The guard "Reverse the collection first" still applies. | On the local copy of prod, the last 60 days had about 1,400 Logiswift moves outside the table: pending_confirmation to out_for_delivery (1,223), out_for_delivery to cancelled (120), pending to delivered (275), cancelled to delivered (5) and more. Blocking them would break daily orders after v2. The 3PL reports where the parcel really is. |
| D2 | Does an integration jump to delivered need a delivery partner? | No. (Also no agent is needed for an integration move to out_for_delivery.) A forced move by a person to delivered still needs a partner (F-302). | 3PL updates arrive with no partner in our system. Blocking them would stop real orders. |
| D3 | Agent "reschedule" (out_for_delivery back to pre-dispatch) | It becomes `failed_delivery` with `failureReason = rescheduled` and a `nextAttemptDate`. The agent app sends that. | The F-301 table has no move back to pre-dispatch. `rescheduled` is already a failure reason, and the KPI layer counts attempts correctly this way. |
| D4 | Actor for import, checkout, settlement and calls with no user | Checkout and Paystack settlement: `system`. CSV re-import status changes: `integration`, with the importing user id kept in the history row. Service calls with no user (scripts, tests): `system`. | Import is bulk data from outside, like a 3PL feed. |
| D5 | inventory_manager can not reach the status route today | Add a narrow permission `orders:update_status` to the inventory_manager defaults (not `orders:update`, which would also let it edit any order field). PATCH status accepts `update` or `update_status`. The machine's role gate still limits it to pre-dispatch moves. | The PRD gives this role pre-dispatch moves only. Narrowed after an automated security review. |
| D6 | Key for the failed-delivery fee | Per attempt: one fee per `failed_delivery` move (keyed on the OrderHistory row). With no FeeRule the fee is 0 and nothing posts. | Each failed attempt costs a fee. The app path has no Delivery row to key on. |
| D7 | Can a returned order be delivered again and post revenue again? | Yes. A return posts a reversal that links to the revenue entry it reverses. A new revenue entry posts only when the order has no revenue entry that is still active (not reversed). | Today a second delivery posts nothing and a second return posts nothing. |
| D8 | Stock during the move to the machine | Each writer keeps its current stock behaviour exactly (the `legacyStockHook` seam). `completeDelivery` still does no stock work. | The plan keeps stock unchanged until M4. Routing completeDelivery through the old hook would add the double decrement to agent completions. |
| D9 | `PUT /orders/:id` writes status with no checks | A status in that body goes through the state machine. Other fields save as today. | It was a hidden writer with no history row and no side effects. |
| D10 | Kanban drag-and-drop to a move the table blocks | The API answers 409 `INVALID_TRANSITION`. The board shows the error and moves the card back. | No silent bypass of the rules. |
| D11 | New permission defaults and tenants that already saved their own permissions | The permission merge stays shallow. A tenant that saved its own `orders` list keeps it. So `orders:force_status` and inventory_manager `update` reach those tenants only when an admin ticks them in the role matrix. super_admin can always force. | A deep merge could give back a permission that an admin removed on purpose. |
| D12 | Can the `system` actor make integration jumps? | No. Only `integration` and `ai` actors jump. System actors (checkout, settlement) make normal table moves only. | No system path needs a jump today. |
| D13 | Sales rep ownership | A rep owns an order when `customerRepId` is the rep. An agent owns it when `deliveryAgentId` is the agent. The old helper `checkResourceOwnership` reads a field that does not exist (`assignedRepId`); the machine does not use it. | Found by job A. |
| D14 | Revenue entry for prepaid physical orders (codAmount 0) | Keep today's rule for each path in COD-10: the status path posts revenue only when `codAmount > 0`; agent completion posts as it does today. COD-14 (order-versus-ledger job) measures the gap and fixes the rule with evidence. | Changing what posts to the ledger without data could double count Paystack money. |

## COD-11 — KPI base, revenue and rates

| # | Question | Decision | Why |
|---|---|---|---|
| D15 | COD-11's checks use the fixture, but the fixture (T23) is in COD-12 | Build T23 (fixture part 1) inside COD-11, before the KPI tests that need it. T24 (fixture part 2) stays in COD-12. The fixture lives in its own tenant `fixture-numbers`, so it never mixes with real data on the local copy. | The plan's "done when" numbers (92,000, 71%, 48%) cannot be checked without it. |
| D16 | When does a returned order leave revenue? F-250 says "leaves the delivery day"; F-900 says it stays in its delivery month and leaves in its return month. | Follow F-900 and the M1-T16 row. The booked delivery time comes from the `delivered` history row, because the machine clears `deliveryDate` on return. | F-900 is the revenue rule; F-250's line is an edge-case note. Closed months must not change. |
| D17 | Yield: F-251 says confirmation × success; F-1008 and M1-T17 say delivered ÷ placed on closed day cohorts. | Follow F-1008 (closed cohorts; a cohort closes when no order is open or 30 days after its placement day). | The two agree once every order is closed. F-1008 is the yield rule. |
| D18 | Which field is "the rep" in rate filters? | `customerRepId` for confirmation rate and yield; `confirmedById` for delivery success (F-252). `partnerId` is `deliveryAgentId` everywhere. | Follows F-252. |
| D19 | Who can read `/api/kpi/*`? | **Revised after a security review.** Permission `analytics:view`, as `/api/analytics`, AND the same role scope: a sales rep sees only orders assigned to them (`customerRepId`), a delivery agent only their own deliveries (`deliveryAgentId`). The scope overrides any `repId` or `partnerId` in the query. Every new KPI route follows this rule. | The first version let a rep read tenant-wide revenue and other reps' rates, which `/api/analytics` does not allow. |

## COD-12 — Rep, leadership, product and partner KPIs

| # | Question | Decision | Why |
|---|---|---|---|
| D20 | How are operating hours stored? | JSON in `SystemConfig.operatingHours`: `{ days: { monday: { open, close, enabled }, ... }, firstCallTargetMinutes, queueWaitAlertMinutes }`. No new columns. One window per day, no overnight windows. Set by `npm run set:operating-hours` (dry by default) or `PUT /api/admin/settings` (shape is checked). | No migration needed; the Operations tab (M7) edits the same JSON. |
| D21 | Partner rate basis | Cohort basis (orders placed in the range, current status). Jump orders count in the rate but not in the timings. | Same default as the store rate. The M4 partner page can add a delivery basis. |
| D22 | What is an auto-confirmed order for time to first call? | Its earliest call has `source = auto_confirm`. Nothing writes that source yet (M7). | Keeps the split ready without guessing from other fields. |
| D23 | A first call logged before the order was created | Counts as 0 minutes. | COD-10 already clamps new call start times to the order creation time. |
| D24 | Who can read `GET /api/reports/team`? | super_admin, admin and manager only. A sales rep gets 403 and uses `GET /api/users/reps/performance`, scoped to their own id. | The team report shows every rep; D19's rule is that a rep sees only their own numbers. |
| D25 | What counts as "Not reachable"? | Calls with outcome `not_reachable` or `no_answer`. The mockup figure (540) is sample text, not a fixture number; the fixture gives 601. | M1.md says `no_answer` becomes `not_reachable` in M7 (F-324), so they are the same outcome. |
| D26 | "Calls per confirmation" | Calls in the range divided by orders confirmed in the range. | Plain reading of the tile; no spec row defines it differently. |
| D27 | Earnings in the rep performance API | Keep `totalEarnings` and `monthlyEarnings` as they are (they read `commissionPaid`). No rate reads them. They move out when `CommissionEntry` exists (F-767). | Out of COD-12 scope; removing them now breaks the reps page with nothing to replace it. |
| D28 | NUMBERS.md says Confirm agent 70% confirmation, but the fixture gives 328 / 465 = 70.5% (shown 71%) | Keep the fixture. Adwoa 640 / 871 = 73.5% (shown 73%) and Confirm agent cannot both match: moving one order to make Confirm agent 70% makes Adwoa 74%. The check asserts the counts and 71%. Rate checks round once, from the counts; the stored 1-decimal value must not be rounded again. | The NUMBERS.md percentages were rounded by hand; the counts (640, 328, 1,026 of 1,445) are the source. |
| D29 | Leadership rounding | Planned AOV (average order value) is rounded to the whole currency unit (244.68 to 245). Orders needed a day is rounded half up. It reads the `confirmation_rate` and `delivery_success_rate` targets (defaults 70 and 60); a `planned_aov` target overrides the default AOV. | Matches NUMBERS.md (245, 56 a day). Unrounded AOV gives 56.5. |
| D30 | `lever()` formula (the PRD gives none) | F-205: delivery success gain = projected confirmed × 5 points × AOV; confirmation gain = projected placed × 5 points × success rate × AOV. The rate furthest under its target wins; null when none is under. | Only written formula in the specs. |
| D31 | Product units | Returned orders are left out of units completely (revenue keeps them until the return month, D16). Free bundled digital lines (price 0) are not counted. | A unit count is "what the customer kept". |
| D32 | Leadership role scope | Same as D19: a rep or agent gets numbers from their own orders; the store targets still show. | D19 applies to every KPI route. |
| D33 | Fixture part 2 shape | January to September history orders have no rep, partner or calls. Margin history (11% Q1, 12% Q2–Q3) comes from `Expense` rows without GL entries; partner cash is `AgentBalance` only. Checks on October data filter `created_at >= 2026-10-01`. | Enough for pace, year and margin trends; GL posting of history is not needed by any M1 check. |
| D34 | Query filters for admins on KPI routes | One shared rule (`kpiScope` in utils/kpiRequest.ts) for every KPI route: a sales rep gets their own `repId`, a delivery agent their own `partnerId`, and any other id in the query is ignored for them. Admins and managers may filter by `repId` and `partnerId` on every KPI route, including revenue and leadership. | One rule for all routes holds D19 by construction. Filtering is a read of data admins can already see. |
| D35 | `financial_summary` (MCP) date window | New `period: 'custom'` with `dateFrom` and `dateTo`, both inclusive store-zone days. The old periods stay. | The fixture check needs exactly 1 to 17 October; the other periods cannot give it. |
| D36 | `analytics_weekly` and `analytics_monthly` checks | They cannot take 1 to 17 October (Monday-to-Sunday weeks, calendar months). The weekly check adds days 1 to 4 (daily tool) to the weeks of 5 and 12 October; the monthly check reads October whole. Both rely on the fixture having no delivery after 17 October. | Tests the tools as they are; no new parameters for a check. |
| D37 | `reps_performance` and `agents_performance` (MCP) range end | Left as it was (end exclusive). Only tools that take a single date or a custom range got the inclusive `to`. | Changing the range rule of these tools is outside M1-T26; it changes no M1 number. |
| D38 | GL 4020 name | Digital Revenue, as in the tenant defaults (`glAccounts.ts`). `seed.ts` calls it "Shipping Revenue"; the seed name is wrong and is fixed when the seed is next touched. | Tenant defaults are what live tenants get. |
| D39 | Financial summary revenue and expenses | `totalRevenue` is the KPI delivered revenue. `digitalRevenue` (GL 4020) is a breakdown field and is not added again. GL 5060 Paystack fees is now in `totalExpenses`, so profit and margin drop by the fees. | 5060 is an expense account that the old "all 5xxx" list missed. |
| D40 | `GET /api/financial/profit-margins` | Deleted with its service, controller, frontend call and store state. No widget showed it; the Finance cards read `summary.profitMargin`. | M1-T25 item 4. |
| D41 | Left on the old definitions in M1 | Agent `onTimeRate`; the old financial reports and profitability endpoints; the frontend "delivery rate trend" and the rep dashboard's "My Conversion Rate" (both computed in the browser). They stay in the kpiGrep allow-list or move in M3. | Not KPI-layer reads named by an M1 ticket. |
| D42 | Cross-role lists on `/api/analytics/rep-performance` and `/agent-performance` | Each list shows a rep or agent only their own row, but a sales rep can still read the agent list and an agent the rep list. This was the same before M1. Sent to Phase 7 (/cso) for a fix or a ticket. | Not changed by M1; fixing it needs a call on what each role's dashboard shows. |
| D43 | Date ranges from the browser | The frontend sends both bounds as `yyyy-MM-dd` calendar days. The backend reads them with `parseBound` in the store zone: `from` is the start of the day, `to` is the end of the day (inclusive). A full ISO string still works as an instant. Endpoints that did `new Date(endDate)` on a picker range now use `parseBound`. | Plan row #28. The browser zone (Lagos) shifted the dashboard range to start on 30 Sep and dropped the last store hour. |
| D44 | D14: prepaid and Paystack revenue in the ledger | No posting rule change in M1. On the dev copy the order-versus-ledger gap (81 days, ledger 13,280 higher) comes from 56 cancelled or failed orders whose revenue entry was never reversed, not from prepaid orders (dev has 0 prepaid physical orders and 0 Paystack rows). Proposed rule for later: paid physical orders with `codAmount` 0 post DR 1030 / CR 4010 at delivery; then a backfill reverses the legacy unreversed entries. Both need proof on production data (read-only) first, and the backfill runs only at the v2 launch with the owner's OK. The nightly ledger check (M1-T28) now shows these gaps as `ledger_gap` findings. | COD-14 job A measure. Changing GL posting without production evidence could double count. |
| D45 | Who sees `/api/financial/health` | Roles with `financial:view`, not admin only. | Plan T28 spec. The response holds totals and gap days, the same data those roles see in the Financial page. |
| D46 | Order currency | New nullable `orders.currency`. The migration backfills it from the tenant, and a BEFORE INSERT trigger fills it when a write leaves it empty. Changing the store currency later does not change old orders; revenue converts each foreign-currency order at its delivery-day rate. | Decision O6 (orders keep their own currency). A trigger covers every write path (app, scripts, raw SQL). Additive column. |
| D47 | FX provider | ExchangeRate-API Open Access (open.er-api.com): no key, daily, lists GHS and NGN. One call per base currency per day at 06:00 Accra, behind an `FxProvider` adapter. The Settings tab links to the provider (attribution required by its terms). No ad spend tile: the app stores no ad account currency. | Free and enough for a daily rate. The adapter lets us switch provider later. |
| D48 | Backend test memory | The backend `test`, `test:integration` and `test:coverage` scripts run Jest with `NODE_OPTIONS=--max-old-space-size=4096`. The heap grows about 50 MB per suite in every suite (an old per-suite leak, not COD-14 code); the new COD-14 suites pushed the full in-band run past the default 2 GB limit. The leak itself goes to a Backlog ticket. | Unblocks the full suite and CI now; the root cause is outside M1 scope. |
| D49 | Wording guard hits that stay | 12 lines are allow-listed in `wording-allowlist.json`, each with a reason. No UI text changed. The agent pay label "Delivery Rate (per delivery)" is a pay amount (`User.deliveryRate`), not a KPI. The Communications "Delivery Rate" tile is message delivery (sent vs delivered). The Delivery Operations trend stays on its old definition (D41). | Renaming user-facing labels is UI work for M3. Suggested M3 names: "Pay per delivery" and "Message delivery". The guard stops any new use. |
